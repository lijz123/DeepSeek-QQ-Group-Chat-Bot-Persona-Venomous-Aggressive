# Chat Bot

基于 Python、OneBot v11 和 DeepSeek 兼容接口的 QQ 群聊天机器人。
提供 @ / 关键词触发、冷却限流、群聊上下文、人设与离线测试。

## 本次更新：理解优先与自然群聊

- 理解底座 → 会话策略 → 表达风格；先接准语义和对象，再选择毒舌或温和的说法。
- 同成员分段消息合并；明确面向其他人的消息不抢答，按稳定账号与消息关系追踪对象。
- 温和问候／友好开场后延续本段温和语气；普通换话题或群友短暂插话不会让它突然变脸。
- 模型自主决定等待、发一条或自然接着说第二／第三条；补发等待 0.8 秒，单群上限 18 条／分钟。
- 同次生成短理解标签和回复落点；已建立后补发更换／漏掉标签即停止，标签本身不会发到群里。

这些机制不能保证真实模型每次理解正确，也不强制每轮连发。昵称、原话、引用与回复对象仍需严格区分。

## 安装和配置

需要 Python 3.10+，以及已配置好的 OneBot v11 服务（例如 NapCat）。

```powershell
python -m pip install -r requirements.txt
Copy-Item config.example.json config.json
$env:DEEPSEEK_API_KEY = "在这里填入你自己的密钥"#想换gpt的也行，不过deepseek更可爱些，反差感更强
python bot.py --config config.json
```

Windows 双击 `start.bat` 会在本地缺少配置时复制示例配置；仍需先向启动进程提供密钥环境变量。
示例中的 `llm.api_key` 必须保留为 `env:DEEPSEEK_API_KEY`，不要把真实密钥写入公开文件。
OneBot 地址默认是本机 `ws://127.0.0.1:3001`；如设置了 OneBot Token，写到本地 `config.json`，不要提交。
本机服务建议仅监听本机地址，并按实际部署配置认证。

`groups.whitelist` 是空列表，表示不限制群；使用前请在本地配置中填入允许的群号。
`users.blacklist`、机器人名称和触发关键词可在本地配置中自定义。
只在已获群成员知情同意的环境中启用，请避免骚扰和泄露群聊信息。

## 文件说明

- `bot.py`：OneBot 客户端、消息处理、触发与发送。

- `requirements.txt`：依赖。
- `.gitignore`：忽略本地配置、凭据、日志、缓存与备份。

## 数据与能力边界

消息上下文使用 JSONL，把 `sender` 身份信息和 `content` 实际发言分开。
昵称分离适用于所有成员，不按某个昵称写特例；它降低误读，但不保证模型永不出错。
运行时发送者昵称、账号标识和消息内容可能随上下文传给模型服务，请先了解并告知群成员。
图片等媒体目前只识别为标记，不进行实际图像理解。
群聊上下文保存在内存中，重启或超时后清除；本地日志可能包含群号和聊天输出，不要公开。

# QQ 登录与机器人启动指南

适用场景：从 GitHub 下载本项目，在 Windows 上使用，NapCat 与本项目运行在同一台电脑。

## 一、先弄清楚：由谁登录 QQ？

**启动顺序：启动 NapCat → 扫码登录机器人 QQ → 启动 Python 机器人 → 群里测试。**

| 程序             | 作用                         |
| -------------- | -------------------------- |
| NapCat         | 负责 QQ 登录、接收 QQ 消息、发送 QQ 消息 |
| 本项目的 Python 程序 | 负责处理消息、调用模型、生成回复           |

**不是运行 `bot.py` 来登录 QQ。`bot.py` 没有 QQ 扫码登录功能。**

如果配置 NapCat 时已经扫码登录成功，就不需要再登录一次。

## 二、通过 NapCat 登录机器人 QQ

### 1. 启动 NapCat

进入安装 NapCat 的文件夹，按照所使用的安装包运行对应入口：

| 安装方式          | Windows 启动入口                                              |
| ------------- | --------------------------------------------------------- |
| Windows 一键安装包 | 安装完成后，进入生成的目录，双击 `napcat.bat`                             |
| Shell 手动安装包   | 双击 `launcher.bat`；Windows 10 按官方说明使用 `launcher-win10.bat` |

不同版本的入口可能变化，以 [NapCat 官方 Windows 安装说明](https://napneko.github.io/guide/boot/Shell)为准。上述文件属于 NapCat，不在本项目文件夹里。

### 2. 手机扫码登录

1. 按照 NapCat 控制台提示，打开本机 WebUI 管理页面。
2. 使用控制台给出的 WebUI 登录信息进入管理页面，不要公开包含 Token 的地址。
3. 进入 **QQ 登录 → 扫码登录**。
4. 用手机 QQ 扫描页面上的二维码，并在手机上确认登录。
5. 等待 NapCat 显示登录成功，让这个 QQ 加入需要使用机器人的群。

**扫码确认登录的 QQ，就是之后发送机器人回复的账号。** 二维码过期时，在页面刷新二维码后重新扫描。如果 QQ 要求额外安全验证，请按官方提示完成。

登录后保持 NapCat 运行，不要关闭它的进程。

### 3. 确认正向 WebSocket 配置

在 NapCat 的网络配置中，确认已经创建并启用了 **WebSocket 服务端（正向 WS）**，不是反向 WS：

| 设置    | 本机部署示例                  |
| ----- | ----------------------- |
| 监听地址  | `127.0.0.1`             |
| 端口    | `3001`                  |
| 消息格式  | `array`                 |
| Token | 自己设置一个随机密钥，稍后填入本项目的本地配置 |
| 启用    | 开启并保存                   |

**WS Token 与 WebUI 网页登录密码不是同一个用途，不要混填。** 不要把本机 WS 接口暴露到公网。

详情见 [NapCat 官方网络配置说明](https://napneko.github.io/config/basic)。如果已经正确配置，直接进入下一步。

## 三、首次准备 Python 机器人

### 1. 安装 Python

本项目需要 Python 3.10 或以上版本。可以从 [Python 官网](https://www.python.org/downloads/windows/)安装，确保终端能使用 `python` 命令。

### 2. 在项目文件夹打开 PowerShell

解压 GitHub 下载的代码，进入能看到 `bot.py` 和 `requirements.txt` 的文件夹。在文件夹地址栏输入 `powershell`，按回车。

**下面的命令都在这个代码文件夹中执行，不是在 NapCat 文件夹执行。**

检查 Python，并安装项目依赖：

```powershell

python -m pip install -r requirements.txt
```

### 3. 生成本地配置

==仅在没有 `config.json` 时执行：==

```powershell
if (!(Test-Path -LiteralPath config.json)) {
    Copy-Item config.example.json config.json
}
notepad config.json
```

如果已经有自己的配置，不要重新复制覆盖。

主要核对下面这些字段，其他设置可以暂时保留：

| 字段                    | 应该怎么填                                           |
| --------------------- | ----------------------------------------------- |
| `onebot.ws_url`       | 与 NapCat 正向 WS 地址一致；本机示例为 `ws://127.0.0.1:3001` |
| `onebot.access_token` | 与 NapCat 正向 WS 中设置的 Token 完全一致                  |
| `groups.whitelist`    | 填入允许机器人工作的群号，建议首次只填一个测试群                        |
| `llm.base_url`        | 所使用模型服务的兼容接口地址，不要填聊天网页地址                        |
| `llm.model`           | 服务商实际支持的模型名称                                    |
| `llm.api_key`         | 保留为 `env:DEEPSEEK_API_KEY`，真实密钥通过后面的环境变量提供      |
| `persona.name`        | 自己喜欢的机器人名称                                      |

**注意：群白名单 `[]` 表示不限制群，不是禁止所有群。** 编辑后保存；JSON 不支持随意添加注释或多余的逗号。

真实密钥、群号和本地 Token 只放在自己的运行环境中，不要上传 `config.json`，也不要公开相关截图。

## 四、登录 QQ 后，如何启动机器人？

确保 NapCat 已登录、正向 WS 已启用，然后在项目文件夹的 PowerShell 中依次执行：

```powershell
$env:DEEPSEEK_API_KEY = "替换为自己的真实API密钥"
python bot.py --config config.json
```

密钥由使用者自行向模型服务商申请，并确认有可用额度。不要把包含真实密钥的命令或截图发到公开仓库。

也可以在设置密钥后，在**同一个 PowerShell 窗口**运行：

```powershell
.\start.bat
```

**上述两种启动方式二选一，不要同时运行两份机器人。**

`$env:DEEPSEEK_API_KEY` 只对当前 PowerShell 及其子进程生效。不要在这个窗口设置完临时变量后，又从桌面另外双击启动。重新打开 PowerShell 后，需要重新设置密钥。

本项目的 `start.bat` 只负责启动 Python 机器人，**不会替你启动 NapCat，也不会弹出 QQ 登录二维码**。

## 五、怎样确认机器人真的能工作？

1. 机器人控制台出现“连接 OneBot”“已登录”等日志，说明连接到了 QQ 接入程序；这还不等于模型调用成功。
2. 用另一个 QQ 账号进入白名单里的测试群。
3. 在群里真正 @ 机器人账号，再发送“你好”。不要仅输入名称代替 QQ 的 @ 操作。
4. 收到机器人回复，才说明 QQ 登录、消息接收、模型调用和消息发送整条链路已经跑通。

运行期间，**NapCat 与 Python 机器人两个程序都需要保持运行**。只关闭网页管理页面，不等于停止 NapCat；关闭 NapCat 进程则会断开机器人连接。

默认存在冷却和限流，连续测试时请间隔几秒，不要密集刷消息。

## 六、以后每次使用的最短流程

1. 启动 NapCat，确认机器人 QQ 在线；如果提示重新扫码，就在 NapCat 页面重新扫码确认。
2. 在项目文件夹打开 PowerShell。
3. 设置自己的 `DEEPSEEK_API_KEY`。
4. 执行 `python bot.py --config config.json`。

依赖安装和本地配置通常只需要首次完成，修改配置后应重启 Python 机器人使其生效。

停止 Python 机器人：在它的窗口按 `Ctrl+C`。如果也不需要 QQ 接入服务，再通过 NapCat 自己的方式停止它。

## 当前机制与已知边界

### 续聊冷却说明

隐式续聊沿用 3 秒直聊冷却，但改为排队等待，不再因为说得太快就直接丢弃。每群每分钟、全局每分钟、输入过滤和对别人说话等保护仍保留。短窗口允许用户换聊，模型收到的目标始终是用户的新消息，并非继续回答旧话题。

### 旧兼容模式：主动补一句（60%，仅 model_reply_planning=false）

`behavior.second_reply_rate=0.6`：正常模型首条成功发送后，按 60% 概率尝试再补一条，固定等待 0.8 秒后生成（`second_reply_delay_min=0.8`、`second_reply_delay_max=0.8`）。最多补一次，不无限连发；出现同群新消息、结束信号或限流则取消。补发计入每群 18 条/分钟与全局 25 条/分钟，额外生成会增加模型开销。设为 0 可关闭；细节见 `PARAMETERS.md` 的“主动补发第二条”。

### 模型自主决定接话和连发（当前默认）

一条、两条或三条由内容决定，不强制双发。规划回复须完整返回 `action/text/next`；纯文本或缺少 `next` 时先纠正一次，仍不合协议才警告并保守退回单条（可能增加一次请求）。畸形 JSON 不会发进群。

排查一直单条：查看 `logs/bot.log` 的「回复规划」和「本轮结束」。`source=json ... next=wait` 表示模型主动交回话轮；`plain_fallback` / `missing_next_fallback` 表示接口未遵循格式；结束记录 `next_wait` 只表示执行等待，须结合来源区分是否降级。`cancel_event` / `activity_or_target_changed` 表示群活动、对象或关闭状态变化而取消，`rate_limit` 表示限流。决策日志不额外记录提示词、回复正文或密钥。`finish_reason=length` 表示规划输出被截断。修改后重启加载；这些记录不能反向还原旧版本未保存的决定。

`behavior.model_reply_planning=true`：本地门禁选中消息后，模型同次生成回复和 `reply/wait/stop` 决定。可以不发、只说一句，或按语境继续第二/第三条；不再用 60% 抽签。每次准备继续都等待 0.8 秒并检查群里是否有新消息，模型也可以重新选择等人或停止。`model_burst_max_messages=3`（含首条）与 `max_chain` 只是防失控保险，不是固定配额。

话轮判断和文本在同一模型请求中生成，无独立分类调用；规划 JSON 使用 `llm.planning_max_tokens=192` 和原 `llm.max_tokens` 中较大者留出协议空间。真正继续说话仍增加生成费用。每条发送尝试计入单群 18/全局 25 条每分钟，收到同群新消息就取消旧续说；不为 wait/stop 定时空转，不重置续聊轮数。旧 `second_reply_rate=0.6` 留作兼容参数，在此模式不生效。

### 明确纠正后的指代更新

遇到“我说的是……”“你理解错了”“不是A，是B”等，当前目标正文会附带纠正理解提示：先确认说话者、对话对象与被纠正的意思，再按原人设回复；续条也沿用修正后的理解。不把“你”一律当机器人，不把昵称、quote 或旧消息里的纠正词当成当前纠正，不硬改用户原话。

这项增强只调整理解提示，不限制原来的夸张吐槽、接旧梗或嘴硬；配置、记忆窗口、1～3条自主连发、0.8秒等待与限流均不变，也不增加独立模型调用。离线测试验证提示接入、角色隔离和机制回归，不代表真实模型每次都理解正确；重启后应使用原对话及其他成员/第三人指代样本复测。

### 当前回怼落点与连发一致性

模型收到的消息分成“当前话轮前景”和原有历史背景。前景突出当前原话，以及有稳定回复关系的上一轮或明确引用；机器人成功发送后会在内存历史里记录回复对象，不依赖昵称或相邻顺序猜。未知引用不拿另一轮补齐，第三人引用仍属于原作者。旧历史保留，仍可夸张调侃、接旧梗，但应先回应当前的反问、反驳或解释，而不是用旧关键词替代回应。

规划 JSON 增加短 `anchor`（整轮共同回应焦点），与回复同次生成，不是推理过程，也不发到群里。首条有 anchor 时，第二/第三条必须原样沿用；改标签或漏标签会停止这次续发。操作和心态等不同角度可以共享同一轮焦点，不要求内容重复。旧三字段 JSON/旧纯文本继续兼容；没有建立 anchor 的旧协议不强行停连发。

这只是前景组织、生成指导和标签一致性保护，不是完整语义审查：模型可能同标签仍答偏，不能据此宣称理解百分之百正确。没有额外分类 API 调用，提示和短字段会增加少量 token；原模型、温度、预算、0.8秒等待、1～3条上限、限流、组合图片规则均保留。重启后请用原反问样本及正常多角度双发复测。日志 `anchor=True/False` 仅标明是否有标签，不记录标签内容；`anchor_changed` / `anchor_missing` 表示续条被拦截。

### 温和开场的整段会话语气

此前 `greeting_tone` 只覆盖问候这一条，后续 `followup/@/reply/poke` 又回到了默认人格。现在，已识别的问候或 `friendly` 友好档开场在模型主回复成功发送后，会按 `(群号, 成员QQ号)` 保存温和会话。后续正常聊天、游戏短答、换话题、@、引用、戳一戳和同轮第二／第三条都沿用温和指令，不突然回到毒舌。不反复重新问好，也不将语气状态当成必须回复的指令。

- 成功的模型主回复刷新会话时间；沿用 `behavior.followup_window`，当前配置为 120 秒。不是整段对话只能持续两分钟：持续交流会续期，长时间没有成功的主回复才过期。
- 明确“不聊了／不用回／别回复”、简短告别“晚安／拜拜／再见”、静音或明确转向别人时结束；普通换话题、简短回答、笑场不单独清掉温和状态。
- 其他群友短暂插话不让原成员突然变脸，也不会把温和状态传给其他成员或其他群。原有防抢答、对象判断、最多 6 次隐式续聊等路由限制不变；必要时仍需 @ 机器人继续。
- 模型 `wait/stop` 只结束当前连发话轮，不结束整段温和对话。发送失败、未发言、补发、固定／图片／赖床预设不会启动或延长温和会话；预设正文仍按原配置发送，不经模型改写。

无需新配置，也没有额外分类 API 调用。此功能沿用现有问候识别和友好触发规则，不是对任意开场语气的完美语义分类；温和提示已传给生成模型，不等于实际输出绝不会偏离。语气缓存只在内存里，重启清空。修改后重启，用“晚上好啊大肥鱼 → 没呢，还在玩三角洲 → 打钱”及其他成员、结束后重新开场的样本复测。

### 理解优先的三层控制

不再让三层都强化攻击：

1. **理解与交互底座**：当前谁在说、对谁说、评价谁的什么、反问／省略／纠正在做什么；引用归属、协议与安全边界。理解评价对象不等于认同评价，不能为了嘴硬偷换意思。
2. **会话策略**：先决定回答、反驳、接梗、澄清或等待，再决定是否有自然的新补充；沿用当前温和或互怼状态。
3. **表达风格**：`mild/sharp/savage`、短句、梗、群内风格设定与条件示例。临时语气只覆盖风格／互动立场，不能覆盖第一层。旧“一律先否定”“正常疑问也攻击”的绝对化指令已移除，毒舌、夸张和有承接关系的旧梗仍保留。

规划模式在同次生成里先返回两个短标签，不输出分析过程：

```json
{"understanding":{"act":"evaluate","target":"bot_reply"},"anchor":"回应对方嫌回怼轻","action":"reply","text":"嫌火力小？你是聊天还是验收武器呢","next":"wait"}
```

`understanding` 描述的是**当前群友原话**，不是机器人回复的句型。`act` 可为 `greet/ask/answer/evaluate/rebut/clarify/joke/close/other/uncertain`；`target` 可为 `bot_reply/bot/self/third_party/topic/unclear`。其中 `self` 是当前群友自己，`bot_reply` 是群友针对机器人的话；标签须结合真实上下文选择，不为“就这”等词写死含义。拿不准可以短问或等待，不强行选择方便攻击的解释。

首条已给出标签时，同轮补发须保持两个标签；更换或漏掉标签会在发送前停止，日志为 `understanding_changed/understanding_missing`。新用户输入开启新的理解，不永久锁住旧解释。旧三／四字段 JSON 和旧 `ReplyPlan` 调用仍兼容；尚未建立理解标签的旧路径没有该一致性保护，稍后建立后才开始保护。与 `anchor` 保护独立，只有 `text` 发进群，日志只标记 `understanding=True/False`。

**标签一致不等于理解正确。** 同一模型可能从首条就判断错；三层标题也不会自动成为强制执行流水线。离线回归只验证提示、协议、角色隔离和发送控制，真实改善需重启后用反诘／点菜选择／装备评价／第三人引用等对照样本复测。没有额外分类调用，提示及标签增加少量 token；模型、温度、规划预算、温和会话、0.8秒、1～3条上限、限流和预设组合图片均保持不变。若日志提示输出截断，再检查规划预算，不以增加连发条数修复语义。
